# Chapter 24: Probabilistic and Cache Data Structures

## Core Idea
When memory is the scarce resource, an **approximate answer with a known error shape** is often enough and orders of magnitude cheaper than an exact one. In this model the question is always the same: which error can the caller tolerate (false "maybe", a count that is a little off, evicting a slightly-wrong key), and what is the source of truth that corrects it? Figures are dated snapshots; items marked "general knowledge" are background knowledge.

## 24.1 Why approximate: metadata, cache lines and memory budgets
- **Thesis**: exact structures spend most of their memory on bookkeeping, not on data.
- **Mechanism**: a balanced tree storing a million 4-byte integers spends about 12 bytes per node with 32-bit pointers (value plus two pointers), so around two thirds is metadata; with 64-bit pointers the node is about 20 bytes and metadata is about 80%; the floor for exact membership is the size of the data itself. Pointer-linked nodes also scatter across the heap, so lookups miss the processor cache. Small devices and huge key spaces cannot afford this.
- **Trade-off**: you give up exactness or deletion to go below the exact floor.
- **Does not hold when**: the set is small, the answer feeds money or a legal count, or no source of truth exists to correct an error.

## 24.2 Bloom filter: "definitely not" or "maybe"
- **Thesis**: a bit array and a hash function answer set membership with no false negatives and a tunable rate of false positives, using far less space than the elements.
- **Mechanism**: insert = hash the key, take it modulo the array length, set that bit. Query = same hash; a zero bit means **definitely absent**, a one means **maybe present** (another key may have set it). The fewer bits per key, the more collisions and the more false positives; as the array fills, the false-positive rate rises towards 100% (when every bit is one, every query says "maybe"). Use a **fast non-cryptographic hash**: the filter needs spread, not resistance to attack, and the cheaper function is several times faster. Standard practice (general knowledge) uses several hash functions per key; the sizing formula links bits per key, number of hashes and the target rate. **Resizing** is not possible in place, because positions depend on the array length: build a new, larger filter by re-inserting every element, which needs the **source of truth** that holds the elements. **Deletion** is not supported by the plain form (clearing a bit could erase another key); variants exist (counting, cuckoo-style, scalable, partitioned, spectral, tree and distributed forms) and trade space or simplicity for deletion or growth.
- **Typical uses**: skip a storage file that cannot contain a key (ch04 4.4); a cache or CDN node checking whether it may hold an object, going straight to the origin when the answer is "definitely not"; "has this item been shown or sent already" for feeds and mailings where a rare false "already sent" is tolerable; protecting a database from lookups of keys that do not exist (cache penetration, ch06 6.12).
- **Trade-off**: space versus false positives; no enumeration of members; no removal.
- **Does not hold when**: a false positive is harmful and cannot be double-checked, or you must list or delete members.

## 24.3 Cardinality estimation with trailing-bit patterns
- **Thesis**: you can count distinct items in a stream by remembering only the rarest hash pattern seen, in memory logarithmic in the number of distinct items.
- **Mechanism**: hash each item to a uniformly spread integer and note the position of its lowest set bit. In a uniform stream, the chance that this position is k is one in 2^(k+1), so position 0 shows up in half of the items, position 1 in a quarter, and so on. Keep a small bit array and set bit k when position k is seen. Repeats of the same item set the same bit, so duplicates do not matter. The first unset bit marks where the probability ran out: about 2 to the power of that position distinct items. The raw estimate is noisy and biased, so a correction constant is applied (about 0.77 in the basic form), several independent estimates are combined (an average is sensitive to large outliers, so a robust combination is used), and the practical algorithm splits the stream into many buckets. An in-memory data-structure server offers it as a built-in with a **sparse** and a **dense** representation for small and large sets.
- **Trade-off**: a few percent error for kilobytes of memory; the set itself cannot be recovered; union of two estimates is cheap, intersection is not.
- **Does not hold when**: you need the exact number (billing, inventory) or the members.

## 24.4 Approximate counters: count in the logarithm
- **Thesis**: a small field can hold a very large frequency if you store its logarithm and increment it probabilistically.
- **Mechanism**: store v approximately equal to log(1 + n). To count one more event, compute the estimated counts for v and v+1; the gap between them is the error you would introduce by incrementing. Increment with probability equal to the reciprocal of that gap: while the gap is small (small counts) almost every event moves the counter; at large counts, only rarely. The estimate tracks the true count and the precision is high where it matters (the difference between 1, 2 and 5 hits) and low where it does not (a million versus a million and a thousand). In a cache that uses it for least-frequently-used eviction, 8 bits hold the log counter and 16 bits hold the last decrement time in minutes (both inside the 24 bits otherwise used for the LRU clock); the counter saturates at a stated ceiling of about a million. **Decay** is applied lazily at access time: elapsed minutes since the last decrement reduce the counter, and because the counter is a logarithm, each counter step drops the real frequency by a large factor (the increment probability falls as the counter grows); no background thread is needed.
- **Trade-off**: an approximate frequency, a random number per increment.
- **Does not hold when**: counts are small enough for an exact integer, or accuracy at high counts matters.

## 24.5 Approximate LRU by sampling
- **Thesis**: an exact least-recently-used order needs a linked list that costs more memory than it saves; sampling gets close at constant memory.
- **Mechanism**: the exact version keeps a doubly linked list (pointers per node, pointer rewiring on every access, random memory access) and a 32-bit last-access time per object. The approximation keeps only a **24-bit coarse clock** per object (a wrapping counter incremented per second, spanning about 194 days) and, to evict, samples a few random keys (default 5, configurable), computes each key's **idle time** (clock minus last access, adding the wrap length if the clock has wrapped past the stored value), and keeps the worst candidates in a small sorted **eviction pool** of fixed size (16). The pool is an array with copy-on-insert, not a list: at that size it stays in the processor cache and wins. Evict from the best candidate until memory is under the limit. Taking several samples brings the result closer to true LRU. The wrap-around fails only if a key has been idle for the whole span, which is stated to be rare in practice.
- **Trade-off**: occasionally evicts a not-quite-worst key; saves memory for data.
- **Does not hold when**: the eviction order must be exact (for example a policy with business meaning) or the cache is small enough that a list's overhead is irrelevant.

## 24.6 The eviction policy menu
- **Thesis**: pick the policy from the access pattern, and know what each costs.
- **Mechanism**: **no eviction** (reject new writes when full); **least recently used** (evict what has been idle longest; assumes recency predicts reuse); **least frequently used** (evict the least-hit; it holds a key that was popular even through a quiet spell, and decays so stale popularity fades); **random** (needs no bookkeeping; works when access is uniform); **nearest expiry** (evict the key closest to its time to live). Each can apply to **all keys** or only to keys that **have an expiry**, which protects permanent keys from eviction. A simple "evict the oldest-inserted" policy is easy to bolt on but ignores use.
- **Trade-off**: bookkeeping and accuracy versus memory and CPU; LFU adapts slowly to a change in popularity, LRU forgets popular keys after one scan.
- **Does not hold when**: the working set fits in memory (no eviction needed) or every item has a fixed time to live anyway.

## 24.7 Scan-resistant caching with midpoint insertion
- **Thesis**: a plain LRU list lets one large sequential scan flush the entire useful cache.
- **Mechanism**: caches rely on spatial locality (neighbouring rows) and temporal locality (a page used now is used again soon). A table scan touches many pages once each, pushing each to the head of the list and evicting everything else. The fix splits the one list into a **young** sublist (about five eighths) and an **old** sublist (three eighths, configurable). New pages enter at the **head of the old list**, not at the head of the whole list; a page already in the old list that is referenced again is promoted to the head of the young list. A scan therefore churns only the old part and leaves the hot young part intact. (The ratio is configurable in the studied engine; a minimum residence time in the old part before promotion is a common extra guard, general knowledge.)
- **Trade-off**: slightly slower warm-up of genuinely new hot pages; one more knob.
- **Does not hold when**: scans are rare or the cache is much larger than the working set.

## 24.8 Hash tables: why doubling, and probing versus chaining
- **Thesis**: growing by a constant makes n inserts cost O(n^2); doubling makes them amortised O(n).
- **Mechanism**: if the array grows by one slot whenever it is full, inserting n keys copies 1 + 2 + ... + n elements, which is quadratic. If it doubles, the copying work for n inserts is bounded by about 2n (the geometric sum of the sizes at each resize), so each insert is amortised constant time. In practice growth is triggered by a **load factor** (for example half full), not by a completely full array, because collisions increase with fill. Collision handling: **chaining** (a list per slot; lookups walk nodes scattered in memory, poor cache behaviour); **open addressing with linear probing** (stays in adjacent memory, cache-friendly, clusters); **double hashing** (spreads probes with a second hash, which costs CPU and jumps around memory, again cache-unfriendly). No strategy wins everywhere: measure lookup time under your load.
- **Trade-off**: memory slack (empty slots) versus time; resize spikes versus constant growth cost.
- **Does not hold when**: size is known in advance (pre-size once) or latency spikes during a resize are unacceptable (use incremental rehashing, general knowledge).
