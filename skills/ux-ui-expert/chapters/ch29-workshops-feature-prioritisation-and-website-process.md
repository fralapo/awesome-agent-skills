# Chapter 29: Workshops, Feature Prioritisation and the Website Design Process

## Core Idea
Features should come from the intersection of prioritised user needs and prioritised business goals, not from a competitor list. Run the scoping as live workshops with every relevant role in the room, then build a website in content-first order. The UX goal: reduce the time between comprehension and action.

## Pre-Design Sequence (site audit)
Brand attributes (culture, customer, voice, benefit, value; pick the top one plus an "X factor") > stakeholder map (executive, business contact, tech, design, marketing) > current site taxonomy > competitor audit (judge on visitor intent, not looks) > user profiles (behaviour, needs, solutions) > user stories > sitemap > wireframes. Raise content risk at kick-off, decide who writes it and audit it separately; state "migrate old copy" as a scope item rather than assuming it ports.

## Customer Profiles and User Stories
- Ground profiles in real buyers' answers to "why did you buy?"; name, age, challenges (their story), needs. Keep 3 to 5.
- Write a story for every profile with four moments: **find out, engage, return, refer**. Ask how each feature makes users return or invite others.
- Resolve conflicts between profiles with separate paths; the site is non-linear.
- Scaffold commitments (plan, hold, book) to capture intent earlier.

## Prioritising
- **Goal scoring**: rate each stakeholder goal 1-10 on obtainability and desirability; do high-high first; re-run limited to the website. Goals that do not touch the website drop out.
- **80/20**: refuse to build everything.
- **Basket weaving**: per profile list the top three needs; list prioritised business goals; write each on sticky notes in two colours; place each need beside the goals it meets; write ideas at each intersection; each idea becomes a feature, a message or a campaign. Generate with many people before judging; pair unrelated items; turn vague goals into concrete ones ("more engagement" becomes "book a group trip"); borrow vocabulary from analogous offers.
- **Value/difficulty matrix**: x difficulty, y customer value; build easy, high-value first; hard, low-value are cut candidates. Calibrate by placing one known item first. Anchor scores to one business goal. Score with the builders, since their difficulty estimates change what survives. Alternative: MoSCoW (must/should/could/won't) on index cards. Keep three to four priorities per user; about 90 minutes.
- Separate features from messages and to-dos (research, content) before scoring.
- Set technical constraints and budget before brainstorming to limit bloat.
- Choose **matrix** for ranking many ideas against effort; **MoSCoW** for a fixed release scope.

## Page and Site Structure
- Landing page order: attention headline, "is this for me?" self-selection, challenges, solution, social proof, objection handling, call to action. About three entry points, drawn from profiles. Tit-for-tat: each challenge is answered by a matching solution. Headlines speak to visitor self-interest in the customer's own problem language.
- Long scroll: headline, reason to act, social proof, secondary paths at the bottom for those not ready. One main call to action dominates.
- Company site: hero with headline > featured work (manually ranked, "view all") > client proof > articles > call to action. Navigation top left, shallow menus, simple column grid (four, two or one), no overlap of text and images, hover info needs a touch equivalent.
- Reuse proven structures for functional parts; differentiate through visuals and voice.

## Build Order
Purpose, audience and wanted actions > research (audience data, short calls) > sitemap > black-and-white wireframes (content and navigation) > detail pages for key content types > mood board with two or three brand adjectives (hand over to `art-director`) > real content and visuals > build in a tool matched to whoever maintains it. Content first. Cut features to launch on time. Log trade-offs between wireframe and final design. Keep code and style changes with the design lead.

## Reviewing a Developer's Build
Order: messaging and hierarchy, layout and responsive behaviour, motion, copy readiness. Annotate screenshots with arrows and target values ("about two-thirds the size"). Full-bleed images scale to the window; fixed-height modules must not hide navigation arrows. Keep animation minimal, fast and meaningful. Agree a copy handoff date early; placeholder copy is a launch risk. Ask when developers expect notes so rounds do not overlap.

## Mistakes
- Taking a feature list at face value; "feature rightitis".
- Running the exercise alone or with too many profiles.
- Reskinning a broken structure instead of solving the user's problem.
- Complex functionality before validating that it returns customers.
- Visuals before content and structure.

## Checklist
- [ ] 3-5 profiles, each with four-moment story.
- [ ] Goals scored; top 3-4 priorities per user.
- [ ] Developers scored difficulty.
- [ ] Wireframes in black and white before visuals.
- [ ] Content owner and handoff date named.
