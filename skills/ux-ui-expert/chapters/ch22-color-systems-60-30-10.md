# Chapter 22: Color Systems — 60-30-10, Color Theory & Design Tokens

## Core Idea
Choosing web colors "by feel" produces flat or chaotic results; choosing them with the 60-30-10 proportion rule, the color wheel, and the HSL model turns color into a deliberate, checkable system — one that scales from a single page to a palette that changes section by section, and that a team can maintain through semantic design tokens instead of hardcoded hex values.

## Frameworks Introduced

- **The 60-30-10 Rule**: distributes a UI's color budget across three roles, not three arbitrary picks. **60% dominant color** — a neutral or very low-saturation color (white/gray, or a near-black for dark themes) that covers most of the screen without tiring the eye. **30% secondary color** — a supporting color (often carried by imagery/illustration) that reinforces the dominant without competing with it. **10% accent/focus color** — used sparingly, only where the user's attention should land (primarily the primary CTA). The proportion *is* the mechanism: a single color used out of its proportion — e.g., putting the accent color into the 60% role — breaks the hierarchy and makes the real call-to-action blend in instead of standing out. Rockstar's GTA VI site is a worked example: a near-black purple dominates the hero (60%), the illustrations supply the supporting color (30%), and a single pink pre-order button is the only 10% accent on the page.
- **Color Wheel Relationships**: colors are chosen from the color wheel in one of two reliable ways. **Analogous** colors sit next to each other on the wheel — naturally harmonious, lower contrast, good for the 60/30 dominant-plus-support pairing. **Complementary** colors sit opposite each other — higher contrast, good for the 10% accent that needs to visually separate from the other two. Either way, accessibility (sufficient contrast for comfortable reading) is a precondition, not an afterthought — see Ch21's WCAG contrast ratios for the measurable floor.
- **Section-Level 60-30-10 (Micro-Palettes)**: the rule doesn't have to apply once to an entire page — it can be reapplied per section, each with its own dominant/secondary/accent trio tied to that section's content or imagery. GTA VI's "Only in Leonida" section is a worked example: each scene is its own 60-30-10 micro-system with its own accent, and the palette updates as the user scrolls so it stays visually consistent with whatever image or video is showing. This is a deliberate exception to "use few colors" — more colors are justified when each one is serving a distinct narrative section, not when they're just decorative variety, and the contrast/accessibility rules still apply inside every micro-palette.
- **Implementation Pattern — CSS Variables + Scroll-Driven Palette Swaps**: the common implementation for section-level palettes is CSS custom properties (variables) for the active color roles, updated as the user scrolls using GSAP's ScrollTrigger plugin (a free, established JavaScript animation library) to detect which section is in view and swap the variable values accordingly. The visual result (palette "live-updating" with scroll position) is a direct consequence of components reading color from variables rather than hardcoded values — the swap only has to change the variables, not every element.
- **HSL for Generating Coherent Variants**: instead of guessing whether two picked colors "go together," pick one starting color and hold its **H**ue fixed while varying only **S**aturation and **L**ightness. Every variant generated this way is automatically from the same color family and reads as intentional rather than random — this is the practical method behind building a color ramp (Ch18) with a reliable result instead of trial and error.
- **Semantic Design Tokens**: rather than assigning a raw color value (e.g., a specific olive-green hex) directly to an element, assign it to a semantic variable — a design token such as `--color-tertiary` — and have components reference that token's *role* (e.g., a button's `accent` variant maps to `--color-tertiary`) rather than the raw value. The payoff shows up on change: updating one token's value propagates correctly everywhere that role is used, instead of requiring a manual hunt through every element that happened to use that hex code.
- **Free Palette & Contrast Tooling**: **Coolors.co** — browse ready-made template palettes or build a custom one from scratch. **Adobe Color** — generate analogous or complementary colors from a single starting color. A Tailwind-syntax palette generator (e.g., uicolors.app) — turns one input color into a full shade scale, shows a live UI preview, and outputs ready-to-paste framework code. Browser DevTools — the fastest way to extract the exact colors already used on a reference site when matching an existing brand. A contrast checker (see Ch21) — verifies the 4.5:1 minimum in seconds; there's no excuse to skip it given how little time it takes.

## Key Concepts
- **Dominant / Secondary / Accent (60/30/10)**: the three proportional roles a UI's colors are assigned to, in that order of visual weight.
- **Analogous colors**: adjacent hues on the color wheel; naturally harmonious, lower contrast.
- **Complementary colors**: opposite hues on the color wheel; high contrast, good for isolating an accent.
- **Micro-palette**: a section-scoped application of the 60-30-10 rule, distinct from a single global palette for the whole page.
- **Design token**: a semantic variable (e.g., `--color-tertiary`) that stores a color's *role*, referenced by components by role rather than by raw value — the mechanism that makes a future color change a one-line edit instead of a page-wide hunt.

## Mental Models
- Treat 60-30-10 as a budget, not a palette — the question isn't "which three colors," it's "which color gets which proportion of the screen," and a color used in the wrong proportion breaks the hierarchy even if the colors themselves are well chosen.
- Pick colors from the wheel on purpose (analogous for harmony, complementary for contrast) rather than eyeballing whether two hex codes "look fine together."
- When a design needs to feel alive across scroll (storytelling pages, case studies, long narrative sites), think in terms of *one micro-palette per section* rather than forcing one global palette to carry the whole page — then let CSS variables plus a scroll-trigger library do the swapping mechanically.
- Build token names around *role* ("accent", "tertiary", "surface"), never around a specific hex or color name — the role is what stays stable when the brand's actual colors change.

## Anti-patterns
- **Using the accent color outside its 10% role**: putting the focus-point color into the dominant or secondary role erases the exact signal it was meant to provide, making the real CTA harder to spot, not easier.
- **Picking complementary or analogous colors on a different page than the one carrying accessibility checks**: a wheel-correct pairing can still fail WCAG contrast — always check contrast on the final rendered pairing, not just on the wheel relationship in the abstract.
- **Adding more colors "for variety" instead of for narrative structure**: more colors are only justified when each is doing section-specific work (as in a scroll-driven micro-palette); decorative-only color variety is the same anti-pattern Ch18 already flags.
- **Hardcoding a raw color value on individual elements instead of a semantic token**: makes a future palette change require finding every element that happens to use that value, instead of editing the token once.
- **Conveying status or meaning through color alone** (e.g., only a color change to show an error or success state): fails users who perceive color differently (color vision deficiency) — pair color with an icon, label, or pattern so the information survives even if the color doesn't register.

## Key Takeaways
1. 60-30-10 is a proportion rule (dominant/secondary/accent), and it can be reapplied per section as a micro-palette, not just once for an entire page.
2. Use the color wheel on purpose: analogous for harmony, complementary for contrast — then verify the actual contrast ratio on the rendered result (Ch21).
3. Generate coherent color variants by fixing hue and varying saturation/lightness in HSL, rather than guessing.
4. Store colors as semantic design tokens referenced by role, not as raw values hardcoded per element, so a palette change stays a one-line edit.
5. Free tools (Coolors, Adobe Color, Tailwind-syntax generators, browser DevTools, a contrast checker) cover palette generation and verification without custom tooling.
6. Never let color alone carry required information — pair it with an icon, label, or other signal for users who can't perceive the color difference.

## European Accessibility Act (EAA) — Why This Isn't Optional
The European Accessibility Act, the EU directive on digital accessibility, is now fully mandatory for private businesses — it applies to virtually every company's sites and services, with the narrow exception of micro-enterprises (under 10 employees or under €2M annual revenue). In Italy, penalties for non-compliance range from €5,000 to €40,000 per violation. Beyond the legal exposure, roughly 87 million people in Europe have some form of disability — a market large enough that accessible color/contrast choices (Ch21's WCAG ratios, plus never relying on color alone) are a business case, not a favor done for a minority of users.
