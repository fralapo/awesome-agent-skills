# Chapter 14: Applying the Double Diamond Design Process

## Core Idea
No single design process is universally correct — but having a repeatable process (like the Double Diamond) gives structure when a design problem is vague, broad, or you get stuck, and it lets you break a big ambiguous prompt into prioritized, scoped work.

## Frameworks Introduced
- **Double Diamond Process (four phases)**:
  - **Discover** (go wide): explore the problem space — identify user and business problems, audit current designs (what's working/not), gather qualitative data (user research, surveys for pain points) and quantitative data (usage/conversion metrics), and run competitive analysis (screenshot competitors, annotate strategies worth adopting).
  - **Define** (go narrow): synthesize findings from discovery into a decision about what to actually fix; collaborate cross-functionally (product, data, engineering) on feature prioritization and requirements; t-shirt size the prioritized tasks (small/medium/large by rough time estimate) to scope the work.
  - **Develop** (go wide again): explore solutions within the now-scoped problem — sketch/brainstorm multiple directions on paper before jumping into high-fidelity tools, to avoid over-investing in one idea too early.
  - **Deliver** (go narrow again): refine and ship — run multiple rounds of concept/usability testing to validate the solution actually solves the user and business problem, iterate based on feedback, and share with cross-functional partners (legal, communications, etc.) to check broader business impact before launch.
  - When to use: any design problem broad or ambiguous enough that it's unclear where to start — the process itself creates the scoping and prioritization steps.
- **T-Shirt Sizing**: a lightweight technique for estimating relative task size (small/medium/large) without precise time estimates, used during the Define phase to prioritize a backlog of possible design tasks.

## Key Concepts
- **Item/product detail page** (example artifact): a densely-featured page (images, carousel/zoom interactions, details, reviews, recommendations) that's a common source of broad, ambiguous redesign prompts — useful as a template for how much a single page can contain.
- **Competitive analysis**: systematically screenshotting and annotating competitor products to extract strategies and patterns worth evaluating for your own product.
- **Concept/usability testing rounds**: iterative validation cycles in the Deliver phase — typically multiple rounds, not one-and-done — before a design is considered ready to ship.

## Mental Models
- Treat "go wide, then go narrow" as the core rhythm of the whole process — it repeats twice (once for the problem, once for the solution), not once.
- When a design prompt feels overwhelming, that's a signal to run Discover before touching any solution — the ambiguity usually means the problem hasn't been scoped yet, not that the solution is hard.
- Sketch cheaply before building expensively: rough paper/whiteboard exploration in Develop prevents anchoring on a single polished idea too early.

## Anti-patterns
- **Jumping straight to high-fidelity design tools** without first sketching multiple rough directions — risks over-investing in and anchoring on the first idea.
- **Skipping Discover/Define and going straight to a solution** for a broad, ambiguous prompt — without scoping, you can't prioritize which of many possible sub-problems to solve first.
- **Treating the Double Diamond as a fixed, one-size-fits-all script** — the process should be tweaked per project, team, and company; it's a structural aid, not a rigid checklist.

## Key Takeaways
1. Use Discover to widen understanding (qualitative + quantitative data, competitive analysis) before narrowing to a decision in Define.
2. T-shirt size prioritized tasks to make scope concrete before entering the solution-exploration phase.
3. Sketch multiple rough directions before committing to one in a design tool — cheap exploration prevents expensive rework.
4. Budget for multiple testing/iteration rounds in Deliver — validating and refining a solution is rarely a single pass.
