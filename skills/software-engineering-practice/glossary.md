# Glossary

**Acceptance stage** - pipeline stage testing the whole system from a user's perspective in a production-like environment (ch01)
**Announce, don't command** - publish events instead of telling another component what to do (ch05)
**Approval test** - test whose assertion is a reviewed snapshot of output; strong for characterising legacy code (ch03)
**Atomic test** - test isolated from others, runnable in any order (ch04)
**Big ball of mud** - system with no structure, strongly coupled; changes are dangerous (ch05, ch06)
**Blast radius** - how much a change can affect (ch06)
**Branch by abstraction** - technique to change code in the shared line without a long branch (ch02)
**Canary release / blue-green** - ways to introduce a release gradually or switch environments (ch01)
**Characterisation testing** - pinning current behaviour before changing legacy code (ch03)
**Cognitive load (team)** - mental demand of the team's work and context; managed, not zeroed (ch08)
**Cohesion** - related things kept together (ch05)
**Commit stage** - first pipeline stage; fast developer-centred tests (ch01)
**Continuous delivery** - working so software is always releasable (ch01)
**Continuous deployment** - automatically pushing every passing change to production (ch01)
**Continuous integration** - merging everyone's changes at least daily and verifying them (ch02)
**Conway's law** - system structure copies the organisation's communication structure (ch05)
**Coupling** - assumptions one part makes about another; five kinds (ch05)
**Cycle time / lead time** - time from idea to working software in users' hands (ch01)
**Dark launching** - releasing code switched off (ch02)
**Deployment pipeline** - automated machine from commit to releasable artefact (ch01)
**DORA metrics** - deployment frequency, lead time, change failure rate, time to restore (ch08)
**Example mapping** - collaborative technique to derive concrete examples from a story (ch09)
**Feature toggle** - runtime switch hiding unfinished functionality (ch02)
**Fitness function** - automated check of an architectural constraint (ch06)
**Flaky test** - test with different results under the same circumstances (ch04)
**Functional isolation** - each test creates its own entities with unique names (ch04)
**Golden path** - easy, supported way to do a common task on a platform (ch08)
**Humble object** - keep a hard-to-test object trivial; move logic out (ch03)
**Information hiding / abstraction** - parts keep secrets from each other (ch05)
**Internal / external quality** - what developers meet in code / what users perceive (ch07, ch09)
**Predictive TDD** - predicting the result and failure message before running each step (ch09)
**Predictive test selection** - running only tests likely to give information for a change (ch04)
**Refactoring** - changing structure without changing behaviour (ch03, ch06)
**Release candidate** - the output of a commit, to be falsified by the pipeline (ch01)
**Revealed vs predicted value** - value discovered by doing vs forecast in advance (ch06)
**Self-testing code** - code that can be told to test itself and report green (ch03)
**SPACE** - five-dimension framework for choosing productivity metrics (ch08)
**Succession problem** - choosing the order and thickness of slices of work (ch06)
**Temporal isolation** - tests unaffected by when or how often other tests run (ch04)
**Test deciderata** - desirable properties of a test suite: fast, cheap, predictive, design-supporting (ch04)
**Test list** - dynamic list of small behaviours that become tests (ch03)
**Test pyramid** - model advising many fast tests and few slow ones (ch04)
**YAGNI** - build only what you need now, but keep design changeable (ch06)
**You build it, you run it** - the building team operates its service, including on-call (ch08)
