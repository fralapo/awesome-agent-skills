# Chapter 4: CPU, Caches and Memory

## Core Idea
A processor is fast and main memory is slow, so almost every performance fact about a program is a fact about how often it gets to stay inside small, fast storage. In this model the machine is a stack of lookups (registers, caches, translation tables, RAM, disk), each one a cache for the next, and a programmer's access pattern decides which level answers. Protection, isolation and relocation of programs come from the same mapping machinery as speed does.

## 4.1 The fetch-decode-execute loop and what a CPU really is
- **Thesis**: a CPU is a small set of registers plus a loop that fetches an instruction, decodes it, executes it and writes the result back; everything else is an optimisation of that loop.
- **Mechanism**: a program counter points at the next instruction in memory; decode selects which part of the arithmetic-logic unit to use; results go to registers or back to memory. Modern cores add pipelining (several instructions in different stages at once), branch prediction and speculative execution (guess the next instructions and discard them if wrong), out-of-order execution with register renaming, and finally "retirement", where results are committed in the order the program wrote them so that the visible behaviour looks sequential.
- **Trade-off**: speculation and reordering buy throughput but create hidden state (caches, predictors) and make reasoning about ordering between cores subtle (see ch05).
- **Does not hold when**: the code is a tiny loop with perfectly predictable branches; then the pipeline is full and the model "one instruction at a time" is close enough.

## 4.2 Two kinds of volatile memory: SRAM and DRAM
- **Thesis**: fast memory is expensive in transistors and power, cheap memory is slow and needs upkeep; a machine therefore carries a small amount of the first and a large amount of the second.
- **Mechanism**: a static cell (SRAM) is two inverters feeding each other, giving two stable states, plus access transistors; a common cell uses six transistors per bit. It flips in picoseconds but draws power continuously and is awkward to lay out (crossing wires need extra layers). A dynamic cell (DRAM) is one transistor and one capacitor: a charged capacitor means one. The charge is tiny (dozens of extra electrons) and leaks, so the cell must be re-read and rewritten periodically, on the order of tens of milliseconds. Reading is analog: the chip pre-conditions long wires to a middle voltage, senses a whole row of cells at once into a small static buffer at the chip edge, and writes the sensed values back; so a read also refreshes. Because the chip senses a whole row at once, the first access to a row is slow (on the order of hundreds of nanoseconds of preparation, as stated) and its neighbours are cheap.
- **Trade-off**: density and price (DRAM) against speed and simplicity of access (SRAM). Registers and caches are SRAM; main memory is DRAM.
- **Does not hold when**: a design uses another technology (for example persistent or high-bandwidth stacked memory); the same trade-off exists but the constants differ. Dense cells packed close together can interfere: repeated access patterns that make a row leak charge into neighbours (the "row hammer" effect) are a known security issue, mitigated by refreshing more often and other measures.

## 4.3 Caches: sets, ways, tags and lines
- **Thesis**: a cache cannot search all of its contents in one or two clock cycles, so hardware limits where an address is allowed to live and compares only a few candidates at once.
- **Mechanism**: memory is fetched in fixed blocks called cache lines (typically 64 or 128 bytes), because fetching a block costs little more than fetching one byte. An address splits into three parts: the offset inside the line, an index that selects a set, and the remaining bits, the tag. Each set holds a few ways (for example four); the hardware compares the tag against all ways of that one set in parallel. A hit returns the byte; a miss fetches the line from the next level and evicts one way of the set (random choice or least recently used, tracked by flag bits). Writes mark the line "dirty" and the data is written back to the next level only on eviction (write-back), which is cheaper than writing through every time. Real machines stack levels: a small L1 (tens of kilobytes, a few cycles), a larger L2 (around a megabyte), a shared L3 (around ten to fifteen megabytes); figures as stated, a dated snapshot. Most of the silicon of a processor die is cache.
- **Trade-off**: more ways reduce conflicts but cost comparators and latency; larger lines exploit sequential reads but waste bandwidth on scattered ones; inclusive designs (everything in L1 also in L2 and L3) make eviction simple but let activity on another core evict your lines from the shared level, which hurts latency-critical programs; some vendors chose non-inclusive designs.
- **Does not hold when**: you reason about a specific chip; policies (inclusive or not, replacement rule, associativity) differ by vendor and generation. Treat the numbers as illustrations of the mechanism.

## 4.4 Locality, prefetching and the access pattern
- **Thesis**: caches work because programs reuse data they touched recently (temporal locality) and touch data near what they touched (spatial locality). Arranging data and loops to match is the main lever a programmer has.
- **Mechanism**: a sequential scan pays for one miss per line and then enjoys hits for the rest of the line. A prefetcher notices a pattern of misses (for example a constant stride) and fetches the next lines before they are asked for. A victim cache holds the most recently evicted lines between the last cache level and memory.
- **Trade-off**: prefetching can detect a pattern that is not real and then waste bandwidth and evict useful lines. Jumping around memory (pointer chasing, large strides, hash tables with random access) defeats both lines and prefetchers.
- **Does not hold when**: the working set fits entirely in L1 (then layout hardly matters) or the program is dominated by something slower than memory (network, disk, interpreter overhead). In a high-level language most programmers never see the cache, but data layout still decides performance; see ch03 for array versus linked list.

## 4.5 Virtual memory: pages, page tables and protection
- **Thesis**: giving every program the illusion of a private, contiguous address space solves protection, relocation and fragmentation with one mechanism: a translation table between the addresses a program uses and physical addresses.
- **Mechanism**: memory is grouped into pages (commonly 4 KB), because a permission bit per byte would need as much table as data. The address splits into a page number and an offset within the page. A hardware unit (the memory management unit) looks up the page number in a page table that records, per page, whether it may be read, written or executed, whether user programs may touch it, and which physical page it maps to. A missing or forbidden entry raises a fault (the operating system decides what follows: terminate the program, load the page, and so on). Because most of a 64-bit address space is unused, the table is a sparse tree: each level indexes a few address bits and points to the next table or to "nothing here"; on a common 64-bit architecture there are about four or five levels. Only the populated branches cost memory.
- **Trade-off**: a translation can cost several memory reads, so a small cache of recent translations (the translation lookaside buffer, tens to a couple of hundred entries) sits in front. A scattered access pattern can miss in the TLB even when the data is in the CPU cache. Page tables themselves take a non-trivial share of RAM across many processes.
- **Does not hold when**: a system has no memory management unit (small embedded targets), where programs share one flat space and protection is by convention.

## 4.6 What mapping buys: relocation, sharing, wrap-around and huge pages
- **Thesis**: once addresses are translated, many tricks become table entries.
- **Mechanism**: (a) every program can be loaded at the same virtual address regardless of where its physical pages are; (b) physical chips need not be contiguous in the virtual view; (c) two processes can map the same physical page, which is the basis of shared memory between programs; (d) device registers and ordinary memory can be placed in different regions; (e) the same pages can appear at two virtual addresses so that a ring buffer wraps without copying; (f) large pages (for example 2 MB instead of 4 KB) mean fewer table entries and let a small TLB cover far more memory, which matters for programs scanning big arrays.
- **Trade-off**: large pages waste memory when a program uses little of each and are harder for the operating system to find contiguous; sharing needs care about who may write.
- **Does not hold when**: the workload has small working sets; then the default page size is fine.

## 4.7 Putting numbers on it
- **Thesis**: a machine at a few gigahertz gives a third of a nanosecond per cycle; a hit in a small cache takes a few cycles, a miss to memory takes hundreds, a trip to storage is orders of magnitude worse. Reason in ratios, not exact values.
- **Mechanism**: estimate how many accesses a loop makes, which level most of them hit, and multiply. The same reasoning applies to the TLB and to the page-fault path.
- **Trade-off**: such an estimate ignores contention from other cores and from the operating system's own work.
- **Does not hold when**: you need a measured number; use a profiler on the real workload (see ch11).

## 4.8 Logic gates, the clock and instruction cycle in more detail
- **Thesis**: a processor is billions of switches combined into gates, paced by a clock; the instruction cycle is the same four steps repeated.
- **Mechanism**: transistors are on-off switches; combined they form logic gates (for example one that outputs true only if both inputs are true); a few kinds of gate suffice for any calculation. A clock generator pulses at some gigahertz and synchronises the state; more pulses per second means more computation, at the cost of heat and shorter life when overclocked. The cycle: fetch (the program counter's address is copied to the memory address register, the control unit loads the data into the instruction register); decode (the instruction has an operation code, such as add or subtract, and an operand, such as an address); execute (the control unit routes signals to the arithmetic logic unit, which computes and stores the result); then repeat. Several cores run several such cycles in parallel.
- **Trade-off**: a higher clock needs more power and cooling; more cores need parallel programs (ch5).
- **Does not hold when**: the bottleneck is memory, not computation (4.4).

## 4.9 System on a chip, and native versus translated code
- **Thesis**: putting processor, graphics, memory controller and accelerators on one package cuts the distance data travels, which saves time and energy; the price is that components can no longer be swapped.
- **Mechanism**: analogy: making a sandwich with all ingredients in one fridge versus driving to several shops. A system on a chip co-locates cores, graphics, input-output control and a machine-learning engine, so energy per task is low and the integrated memory is close; a conventional design with separate chips for memory and input-output can have individually more powerful parts at a cost in energy and latency. A machine of a different instruction set can run old binaries through a translation layer, usually well, but CPU-heavy workloads suffer and software that is compiled natively for the new architecture does best (the example is a developer's builds on a then-new processor family; the figures are dated).
- **Trade-off**: efficiency and integration versus upgradability and ecosystem readiness.
- **Does not hold when**: your workload is a benchmark the vendor optimised for; benchmarks may not match real projects. Run your own build or test on the machine in question (ch11).
